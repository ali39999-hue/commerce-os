# 🛍️ سیستم‌عامل جامع تجارت الکترونیک (Commerce OS)
### نسخه ۱.۰.۰ — نخستین انتشار پایدار (آبان ۱۴۰۵ / اکتبر 2026)
### نتیجه‌ی سنتز فنی: `itrip-platform` + `aroux30/site` + `commerce-os-starter-v1`

---

## 🌟 معرفی پروژه

**Commerce OS** یک پلتفرم جامع، چندمستأجری (Multi-Tenant) و ماژولار است که نیازهای عمیق بومی‌سازی بازار ایران (درگاه‌های پرداخت شتابی، کارت‌به‌کارت بانکی با فیش، ارسال پستی و تیپاکس و پیک، تقویم جلالی، اعتبارسنجی شبا و کد ملی) را با استانداردهای معماری مالی سازمانی (دفترکل دوبل‌اندر بدون ممیز شناور، رزرو اتمیک انبار، الگوی Outbox، آیدمپوتنسی مطلق، جداسازی تضمین‌شده مستأجرها) ترکیب می‌کند.

معماری انتخابی، **مونولیت ماژولار در مونوریپو** است (ADR-001): چهار اپلیکیشن (`api`، `storefront`، `admin`، `worker`) و شش پکیج مشترک TypeScript با پریزما و PostgreSQL 17. جست‌وجوی فارسی، توصیه‌گر، باشگاه مشتریان، اشتراک دوره‌ای، استعلام عمده B2B، بنیان فروشندگان و کالای دیجیتال در موج‌های W17 و W18 به همین هسته اضافه شده‌اند (ADR-006 تا ADR-012).

## 🖥️ پنل ادمین و مرکز عملیات (ERP)

پنل ادمین تک‌صفحه‌ای (`apps/admin`) با **۱۳ تب** عملیاتی و دکمه خروجی مالی **«دانلود خروجی استاندارد سپیدار (CSV + BOM)»** در نوار بالای پنل:

1. **داشبورد و شاخص‌ها**
2. **سفارشات** (فهرست، جزئیات، گذار وضعیت)
3. **تایید کارت‌به‌کارت** (صف فیش‌های در انتظار با نشان تعداد)
4. **کنترل انبار** (موجودی، هشدار کمبود)
5. **دفترکل دوبل‌اندر** (اسناد و تراز)
6. **لاگ‌های حسابرسی** (AuditLog)
7. **تحلیل و قیف فروش** (اتصال زنده به `/v1/analytics/summary`)
8. **مرکز استثناها** (اتصال زنده به `/v1/ops/exceptions` — پنج بلوک: Dead Letter اوتباکس، پرداخت نامشخص، رزروهای گیرکرده، فیش‌های در انتظار، وب‌هک‌های ناموفق)
9. **کوپن‌ها** (مدیریت و فعال/غیرفعال‌سازی)
10. **اشتراک‌های دوره‌ای** (توقف/ادامه/لغو با هدر مستأجر)
11. **استعلام‌های عمده B2B** (تغییر وضعیت NEW → IN_REVIEW → QUOTED → CLOSED)
12. **فروشندگان** (فهرست زنده + ایجاد فروشنده)
13. **لایسنس‌های دیجیتال** (گرنت‌ها + ابطال)

تب‌های متصل به API با تایم‌اوت کوتاه و پاسخ دمو (Fallback) هنگام عدم دسترس‌پذیری داده واقعی رندر می‌شوند و حالت واقعی/دمو همیشه شفاف است.

## 🔌 ماژول‌های API

سرویس `apps/api` (NestJS 11) شامل **۲۴ ماژول دامنه** است که در `AppModule` ثبت شده‌اند:

- **هسته تجاری:** `identity` (OTP و نشست)، `catalog` (کاتالوگ چندمستأجری)، `search` (جست‌وجوی فارسی با مترادف)، `pricing` (کوت فینگر‌پرینت‌دار و تقسیم پنی)، `inventory` (رزرو اتمیک و TTL)، `checkout` (جلسه چک‌اوت + ثبت سفارش آیدمپوتنت)، `payments` (زرین‌پال، کارت‌به‌کارت، کپچر و کال‌بک)، `orders` (ماشین حالت، فاکتور رسمی، تاریخچه)
- **مالی و عملیاتی:** `ledger` (دوبل‌اندر، تراز آزمایشی، اکسپورت سپیدار)، `shipping` (استعلام نرخ و رهگیری)، `wallet` (تراکنش‌نگار با ردپای منبع)، `outbox` (انتشار رویداد با SKIP LOCKED)، `notifications` (قالب‌های پیام خروجی)، `webhooks` (ارسال امضاشده HMAC و پایش)، `analytics` (۵ رویداد مجاز بدون PII + قیف)، `ops` (مرکز استثناهای پنج‌بلوکی)، `reviews` (نظرات و تعدیل)
- **رشد W17/W18:** `recommendations` (مرتبط/پرفروش/برای شما)، `loyalty` (امتیاز و سطوح)، `subscriptions` (پلن و عضویت)، `b2b` (سرنخ استعلام عمده)، `vendors` (بنیان مارکت‌پلیس)، `digital` (گرنت لایسنس و دانلود توکن‌دار)
- **زیرساختی:** `health` (liveness/readiness) + ماژول دیتابیس

**قرارداد کامل متد/مسیر/بدنه/پاسخ همه مسیرها** در سند مرجع [docs/api/API_CONTRACTS_FA.md](docs/api/API_CONTRACTS_FA.md) نگهداری می‌شود (شامل هدرهای `x-idempotency-key` و `x-tenant-id`، قالب استاندارد خطا با `correlationId`، سقف‌های Rate Limit و وضعیت‌های مرجع دامنه).

## 🔒 اصول غیرقابل مذاکره (Invariants)

1. **محاسبات مالی بدون Float:** تمام وجوه نقدی با واحد **ریال** و به‌صورت `BigInt` در TS و `Decimal(20,0)` در دیتابیس ذخیره می‌شوند (ADR-002). تبدیل به تومان صرفاً در لایه نمایش انجام می‌شود.
2. **دفترکل متوازن دوبل‌اندر:** شرط `SUM(DEBIT) === SUM(CREDIT)` در سطح تراکنش احراز می‌شود؛ ثبت‌ها Append-Only هستند و اصلاح فقط با ثبت معکوس مجاز است.
3. **رزرو موجودی اتمیک و ضد-Oversell:** قفل ردیفی `SELECT ... FOR UPDATE` با ترتیب ثابت شناسه روی ردیف‌های انبار، رزرو موقت با TTL ۱۵ دقیقه و آزادسازی دوره‌ای توسط Worker (ADR-004).
4. **آیدمپوتنسی قطعی:** دستورات مالی با کلید آیدمپوتنسی و هش درخواست ثبت می‌شوند؛ ارسال مجدد همان درخواست عیناً همان پاسخ را می‌دهد و کلید تکراری با بدنه متفاوت خطای `409 Conflict` می‌دهد.
5. **جداسازی مستأجرها:** هر دسترسی با کلید ترکیبی `[tenantId, ...]` و اکستنشن پریزما محافظت می‌شود؛ مقدار هدر فقط انتخاب‌گر است، نه مجوز دور زدن (دفاع BOLA/IDOR) (ADR-003).
6. **الگوی Outbox:** رویدادهای کسب‌وکاری داخل همان تراکنش تغییر وضعیت ثبت و توسط Worker با `SKIP LOCKED` منتشر می‌شوند؛ شکست‌ها با پس‌زدن نمایی و Dead Letter قابل ممیزی‌اند.
7. **سطح حمله کنترل‌شده:** محدودسازی نرخ پنجره ثابت (۳۰۰ درخواست/دقیقه عمومی، ۱۰ درخواست/دقیقه روی `auth`) با هدر `Retry-After`؛ اعتبارسنجی مقصد وب‌هک در برابر SSRF (مسدودسازی مقصدهای داخلی، با مجاز شدن loopback فقط در توسعه)؛ فایروال PII در آنالیتیکس؛ هیچ بدنه درخواست/پاسخی در لاگ نوشته نمی‌شود و کد پیگیری فقط `correlationId` است؛ خطای 500 هیچ نشتی از استک ندارد.

## 🚀 راهنمای اجرا

### ۱. نصب وابستگی‌ها
```bash
pnpm install
```

### ۲. کلاینت پریزما و پایگاه‌داده — دو مسیر

**مسیر الف — PostgreSQL جاسازی‌شده (بدون نصب هیچ چیز — پیش‌فرض توسعه):**
```bash
# اولین بار: اعمال اسکیما و اجرای سرور (داده‌ها در .pgdata/ ماندگارند)
pnpm --filter @commerce-os/api run db:generate
pnpm --filter @commerce-os/api exec prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script > apps/api/prisma/embedded-init.sql
node scripts/embedded-postgres.mjs        # سرور wire-protocol واقعی روی 127.0.0.1:5432
pnpm --filter @commerce-os/api run db:seed
```
سپس `pnpm dev` را در ترمینال دیگری اجرا کنید. مسیر طلایی ۱۹/۱۹ روی همین دیتابیس سبز می‌شود.

**مسیر ب — PostgreSQL واقعی (Docker یا نصب سیستمی):**
```bash
pnpm --filter @commerce-os/api run db:generate
docker compose up -d                       # یا سرویس PostgreSQL محلی
pnpm --filter @commerce-os/api exec prisma db push
pnpm --filter @commerce-os/api run db:seed
```

سید دمو شامل: مستأجر/فروشگاه، ۸ کالا (۶ فیزیکی + ۲ دیجیتال)، فروشندگان، کاربران، کیف پول، حساب‌های دفترکل، کوپن‌ها، روش‌های ارسال و ۳ پلن اشتراک.
```

### ۳. اجرای کل سیستم در حالت توسعه
```bash
pnpm dev
# یا روی ویندوز: start-dev.bat
```

- **ویترین فروشگاه:** [http://localhost:3000](http://localhost:3000)
- **پنل ادمین ERP:** [http://localhost:3001](http://localhost:3001)
- **هسته API:** [http://localhost:4000/v1](http://localhost:4000/v1)

### ۴. راستی‌آزمایی مسیر طلایی (۱۹ گام)
```bash
node scripts/e2e-golden-path.mjs
```
سلامت → کاتالوگ → جست‌وجوی فارسی با مترادف → استعلام ارسال → چک‌اوت و رزرو انبار → ثبت سفارش با آیدمپوتنسی (بازپخش کلید) → پرداخت درگاه و سند دفترکل → آنالیتیکس و قیف → مرکز استثناها → وب‌هک امضاشده → نظرات → resolve فروشگاه → قالب‌های نوتیفیکیشن → توصیه‌گر → باشگاه مشتریان → پلن‌های اشتراک → سرنخ B2B → فروشندگان → گرنت‌های دیجیتال. خروجی سبز انتشار، صفر FAIL است.

### ۵. بارسنجی سبک‌وزن
```bash
node scripts/load-check.mjs --target http://localhost:4000 --n 60 --c 10
```

```bash
pnpm test    # vitest پکیج‌ها + jest سرویس API

```

### ⚠️ وضعیت DB-gated (صادقانه)

با **مسیر الف (PGlite جاسازی‌شده)** مسیر طلایی کامل ۱۹/۱۹ سبز است. اگر دیتابیس در دسترس نباشد، سیستم **نمی‌شکند اما صادقانه کم می‌آورد**:

- **پاسخ‌های FALLBACK دمو:** کاتالوگ، جست‌وجو، قیمت‌گذاری، توصیه‌گر، پلن‌های اشتراک، فروشندگان و نوتیفیکیشن‌ها داده دمو با `source: FALLBACK` برمی‌گردانند؛ نظرات، آنالیتیکس، گرنت‌های دیجیتال و باشگاه مشتریان با `dbAvailable: false` پاسخ می‌دهند؛ سرنخ B2B پذیرفته ولی در حافظه لاگ می‌شود (`persisted: false`) و ثبت عضویت اشتراک با `503` صادقانه رد می‌شود.
- **گام‌های وابسته به DB مسیر طلایی (گام‌های ۵ تا ۷: چک‌اوت، ثبت سفارش، کپچر پرداخت)** با وضعیت `SKIP` شفاف می‌شوند.
- **ویترین** هرگز داده ساختگی را جای کاتالوگ واقعی نمی‌گذارد (پیام «کاتالوگ در حال اتصال است»)؛ صفحات کلاینت‌محور (علاقه‌مندی، مقایسه، سبد) و پنل کاربر با داده دمو کار می‌کنند.

فعال‌سازی واقعی: `docker compose up -d` (PostgreSQL 17 + Redis 7) سپس `db push` و `db:seed`. برای استقرار کامل شش‌سرویسه (api/worker/storefront/admin + پایگاه‌داده) از `docker-compose.prod.yml` استفاده کنید و چک‌لیست انتشار (`docs/architecture/RELEASE_CHECKLIST_FA.md`) را پیش از تگ نسخه طی کنید.

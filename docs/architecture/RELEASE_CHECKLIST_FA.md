# چک‌لیست انتشار — Go/No-Go (نسخه خلاصه گیت‌های A تا L)

این سند، نسخه عملیاتی و خلاصه گیت‌های انتشار سند مادر (COMMERCE_OS_UNIFIED_SYNTHESIS و قراردادهای API) است. پیش از هر تگ نسخه، همه ۱۲ گیت باید **سبز با شواهد عینی** باشند؛ «ظاهراً خوب است» پذیرفته نیست. مسئول هر گیت، نتیجه را با شماره build/commit در تیکت انتشار ثبت می‌کند.

قاعده اجرا: هر گیت شرط عینی (قابل اندازه‌گیری) دارد. یک آیتم قرمز در هر گیت = **No-Go**. آیتم‌های «کاستی ثبت‌شده» فقط با پذیرش مکتوب مالک محصول و بدون عبور از گیت‌های صحت تجاری و امنیت مجازند.

---

## گیت A — صحت تجاری: دفترکل متوازن

- [ ] `GET /v1/ledger/trial-balance` (با هدر `x-tenant-id` مستأجر واقعی) پاسخ `200` می‌دهد و برای همه حساب‌ها `SUM(DEBIT) === SUM(CREDIT)` است؛ انحراف صفر ریال.
- [ ] کوئری راستی‌آزمایی روی پروداکشن/staging: `SELECT COALESCE(SUM(CASE direction WHEN 'DEBIT' THEN amount ELSE -amount END),0) FROM ledger_entries;` باید `0` برگرداند.
- [ ] هیچ ثبت دفترکل ویرایش یا حذف نشده است (فقط ثبت معکوس `REV-...` مجاز است).
- [ ] سند فروش یک سفارش نمونه کامل (شامل مالیات ۱۰٪ و هزینه ارسال) به حساب‌های `1010/1020` بدهکار و `4010/4020/2030` بستانکار درست ثبت شده است.

## گیت B — صحت تجاری: آیدمپوتنسی

- [ ] `POST /v1/checkout/place-order` با تکرار همان `x-idempotency-key` و همان بدنه، عیناً پاسخ اول را برمی‌گرداند و فقط یک سفارش ساخته می‌شود (`idempotency_records.status = COMPLETED`).
- [ ] همان کلید با بدنه متفاوت پاسخ `409 Conflict` می‌دهد.
- [ ] double-click واقعی (دو درخواست هم‌زمان) روی place-order در staging دقیقاً یک `orders` و یک `payment_intents` ایجاد می‌کند.
- [ ] callback تکراری زرین‌پال برای یک intent فقط یک capture تولید می‌کند (پاسخ دوم شامل `alreadyCaptured: true`).

## گیت C — صحت تجاری: صفر Oversell

- [ ] آزمون هم‌زمانی: خرید هم‌زمان تعدادی کلاینت روی آخرین واحد موجودی هر واریانت، دقیقاً به تعداد موجودی موفق می‌شود و بقیه با پیام کمبود موجودی رد می‌شوند.
- [ ] پس از آزمون: `SELECT SUM(reserved_qty) FROM inventory_levels` با رزروهای `ACTIVE` منطبق است و هیچ `reserved_qty` منفی وجود ندارد.
- [ ] رزروهای TTL گذشته پس از ۱۵ دقیقه توسط worker آزاد می‌شوند و بلوک `stuck_reservations` در `GET /v1/ops/exceptions` خالی است (RB-03).
- [ ] خطوط سفارش ثبت‌شده با `on_hand − reserved − sold` انبار سازگار است.

## گیت D — امنیت: Rate Limit فعال

- [ ] `RATE_LIMIT_GLOBAL_PER_MIN` و `RATE_LIMIT_AUTH_PER_MIN` در `.env` پروداکشن تنظیم شده‌اند (پیش‌فرض ۳۰۰ و ۱۰ در دقیقه به‌ازای هر IP).
- [ ] ارسال ۱۱ درخواست متوالی به `/v1/auth/otp/request` از یک IP، درخواست یازدهم را با `429`، هدر `Retry-After` و بدنه استاندارد خطا (شامل `retryAfterSeconds`) جواب می‌دهد.
- [ ] عبور از سقف ۳۰۰ روی مسیر عمومی نیز `429` می‌دهد و پاسخ شامل `correlationId` است.
- [ ] جعل نشده: پاسخ 429 هیچ اطلاعی از شمارنده داخلی یا stack نمی‌دهد.

## گیت E — امنیت: Secrets چرخیده و مدیریت‌شده

- [ ] همه مقدارهای `.env.example` (نمونه‌های توسعه) در پروداکشن جایگزین شده‌اند: `AUTH_SECRET`، `ENCRYPTION_KEY`، `WEBHOOK_SECRET`، `POSTGRES_PASSWORD` — با `openssl rand -hex 32` و پیش از اولین ترافیک واقعی.
- [ ] `ZARINPAL_SANDBOX=false` (و سایر درگاه‌ها روی واقعی) و `MERCHANT_*` برابر اطلاعات واقعی فروشنده است.
- [ ] `.env` در `.gitignore` است، هرگز کامیت نشده و خروجی `git log --all -p -- .env` خالی است (اسکن secrets در CI هم خالی).
- [ ] `DATABASE_URL` با هاست سرویس (`postgres`) و رمز قوی هم‌خوان `POSTGRES_PASSWORD` است؛ `ENCRYPTION_KEY` پس از شروع عملیات تغییر نکرده است (یا RB-05 کامل اجرا شده).

## گیت F — امنیت: CORS و ایزولاسیون محدود

- [ ] `CORS_ORIGINS` به دامنه‌های واقعی محدود شده است؛ تا زمان اعمال در کد، فیلتر `Origin` برای `/v1/*` روی reverse proxy فعال است (وضعیت فعلی `origin: true` با پروداکشن ناسازگار است).
- [ ] ترمینیشن TLS روی reverse proxy فعال است و فقط پورت‌های 80/443 (و SSH) از اینترنت بازند؛ پورت‌های 5432 و 6379 منتشر نیستند (`docker compose -f docker-compose.prod.yml ps` تأیید می‌کند).
- [ ] endpointهای مالی/ادمین بدون `x-tenant-id` پاسخ `401` می‌دهند و مستأجر A هیچ داده‌ای از مستأجر B نمی‌بیند (آزمون BOLA روی `ledger` و `wallet`).
- [ ] همه کانتینرهای اپلیکیشن با کاربر غیر root اجرا می‌شوند و ایمیج‌ها multi-stage هستند.

## گیت G — UX/کیفیت: مسیر طلایی E2E سبز

- [ ] `node scripts/e2e-golden-path.mjs` روی build پروداکشن (پس از `up -d` و مایگریشن) تمام گام‌ها را PASS می‌دهد: سلامت، کاتالوگ، جست‌وجوی فارسی با مترادف، قیمت‌گذاری، ارسال، چک‌اوت.
- [ ] هیچ گامی SKIP نخورده باشد (SKIP یعنی زیرساخت بالا نیست — اول رفع شود).
- [ ] جریان کامل پرداخت زرین‌پال در سندباکس تا `PAID` + پیامک `ORDER_PAID` + سند دفترکل بسته می‌شود؛ فیش کارت‌به‌کارت تا تأیید ادمین (`C2C_RECEIPT_APPROVED`) تست شده است.
- [ ] ورود OTP (request → verify → `/auth/me`) و گذار وضعیت سفارش از طریق `/orders/:id/transition` در همین run پاس می‌شود.

## گیت H — UX/کیفیت: Core Web Vitals

- [ ] اندازه‌گیری Lighthouse (موبایل، صفحه نخست و صفحه محصول استورفرانت): LCP ≤ ۲.۵s، INP ≤ ۲۰۰ms، CLS ≤ ۰.۱ در محدوده هدف.
- [ ] فونت Vazirmatn و اعداد/تقویم فارسی (جلالی، `Intl fa-IR`) بدون فلش (FOUT/FOIT محسوس) بارگذاری می‌شوند و چیدمان `rtl` در همه صفحات سالم است.
- [ ] فاکتور رسمی (`/orders/:id/invoice`) در چاپ مرورگر بدون شکستگی رندر می‌شود (اعداد، جدول، ارقام ریالی).
- [ ] بودجه عملکرد (bundle size صفحات بحرانی) نسبت به نسخه قبلی بدتر نشده باشد؛ رگرسیون > ۱۰٪ نیازمند توجیه است.

## گیت I — عملیات: Health و Ready

- [ ] `curl http://127.0.0.1:4000/v1/health` پاسخ `{"status":"ok","service":"commerce-os-api"}` و `curl /v1/ready` پاسخ `{"status":"ready","dependencies":{"postgres":"ok"}}` می‌دهد.
- [ ] `docker compose -f docker-compose.prod.yml ps` همه شش سرویس را `healthy` نشان می‌دهد (healthcheckهای image-level فعال‌اند).
- [ ] تست منفی: با توقف موقت postgres، `/v1/ready` بلافاصله `503` با `postgres: unavailable` می‌دهد و پس از بازگشت سرویس، بدون ری‌استارت دستی سالم می‌شود.
- [ ] لاگ‌ها ساختارمند (JSON) و بدون body درخواست/پاسخ‌اند؛ هر خطای 5xx یک `correlationId` قابل ردیابی دارد.

## گیت J — عملیات: بکاپ تست‌شده

- [ ] بکاپ روزانه `pg_dump -Fc` فعال است (cron ثبت‌شده) و فایل امروز با checksum (`sha256sum`) تأییدشده موجود است.
- [ ] کپی off-host طبق قانون ۳-۲-۱ تأیید شده است (حجم + checksum برابر).
- [ ] آخرین تمرین restore فصلی در staging طبق RB-06 موفق بوده و RTO اندازه‌گیری‌شده ≤ ۴ ساعت و RPO پوشش‌داده‌شده ≤ ۱ ساعت است (گزارش تمرین آرشیو شده).
- [ ] `pg_restore --list` روی جدیدترین فایل بدون خطای ساختاری است و توازن دفترکل پس از restore در تمرین صفر بوده است.

## گیت K — عملیات: ران‌بوک‌ها موجود و گرم

- [ ] شش ران‌بوک `docs/runbooks/RB-01` تا `RB-06` موجود، مرورشده و با نسخه فعلی کد هم‌خوان‌اند (نام جدول‌ها/مسیرها دوباره راستی‌آزمایی شده).
- [ ] دسترسی‌های اجرای ران‌بوک (دسترسی docker و `psql` به پروداکشن، دسترسی پنل زرین‌پال برای استعلام verify) برای نفر پشتیبان آزمایش شده است.
- [ ] شماره تماس/کانال تشدید (escalation) و مالک هر ران‌بوک در تیکت انتشار ثبت است؛ تیم روی سناریوی شبیه‌سازی‌شده RB-01 یا RB-02 تمرین اخیر دارد.
- [ ] `GET /v1/ops/exceptions` پیش از انتشار خالی یا در حد نویز است (شمارش هر بلوک صفر یا توضیح‌داده‌شده).

## گیت L — بسته‌بندی انتشار و بازگشت

- [ ] نسخه tag شده است (`git tag vX.Y.Z`) و ایمیج‌های چهار سرویس با همان tag ساخته و در registry لوکال/remote در دسترس‌اند (پیش‌شرط RB-04).
- [ ] تغییرات schema فقط به‌صورت expand/contract است؛ مایگریشن ترکیبی یا مخرب (drop ستون مصرف‌شده) در این نسخه وجود ندارد و `pnpm exec prisma migrate status` پس از deploy سبز است.
- [ ] `CHANGELOG` نسخه (تغییرات کاربر-پیدا و ریسک‌ها) نوشته شده و پنجره سازگاری contractهای API (`docs/api/API_CONTRACTS_FA.md`) حفظ شده است؛ هر تغییر قرارداد، breaking نیست یا نسخه‌بندی شده است.
- [ ] نقشه rollback مکتوب است: tag قبلی، وضعیت مایگریشن‌ها (expand نگه‌داشته می‌شود)، و مسئول اجرای RB-04 مشخص است.

# RB-05 — افشای Secret (نشت کلید امضا/رمزنگاری/وب‌هک)

| فیلد | مقدار |
|---|---|
| شناسه | RB-05 |
| شدت | بحرانی (Critical) — PII، توکن نشست‌ها و اعتبار وب‌هک‌ها در معرض است |
| دامنه | `.env` (AUTH_SECRET · ENCRYPTION_KEY · WEBHOOK_SECRET) · `user_sessions` · داده‌های رمزشده PII (`enc:v1:...`) · تاریخچه گیت |
| سرویس‌ها | `api` · `worker` · مخزن کد |
| SLO اجرا | حداکثر ۶۰ دقیقه تا مهار کامل |

## ۱. علائم (Symptoms)

- مقدار `AUTH_SECRET`، `ENCRYPTION_KEY` یا `WEBHOOK_SECRET` در commit، issue، لاگ عمومی، اسکرین‌شات، پیام گروهی یا ابزار اسکن secrets شناسایی شده است.
- لاگ خطاها (stack یا dump) حاوی مقدار متغیرهای محیطی بوده و در جایی اشتراک شده است.
- رفت‌وبرگشت مشکوک: نشست‌های ناشناس معتبر، امضاهای `x-commerce-signature` جعلی تأییدشده، یا رکوردهای رمزشده باز شده در دسترس اشتباه.
- `git log -p .env` یا ابزارهایی مثل gitleaks برای الگوی مقدارهای `.env.example` (۶۴ کاراکتر hex) hit می‌دهند.

## ۲. تشخیص (Diagnosis)

1. **دامنه افشا را مشخص کنید:**
   - کدام Secretها؟ (`AUTH_SECRET` امضای توکن/نشست، `ENCRYPTION_KEY` رمزنگاری PII با AES-256-GCM، `WEBHOOK_SECRET` امضای HMAC-SHA256 خروجی.)
   - از کجا؟ تاریخچه گیت، لاگ، بکاپ، خط تولید CI؟
   - از کی؟ برای تعیین پنجره اعتبار داده‌ها و نشست‌های مشکوک.
2. **سرریز به مخزن را بسنجید:**

```bash
git log --all --full-history -p -- .env | head
# جست‌وجوی الگوی مقدار در کل تاریخچه
git grep -n "<LEAKED_VALUE>" $(git rev-list --all) 2>/dev/null | head
```

3. **نشست‌های فعال و داده‌های رمزشده را بشمارید** (برای سنجش اثر بعد از چرخش):

```sql
SELECT count(*) AS active_sessions FROM user_sessions WHERE expires_at > NOW();
SELECT count(*) AS sessions_all    FROM user_sessions;
```

4. تصمیم بگیرید: افشای `AUTH_SECRET`/`WEBHOOK_SECRET` چرخش ساده است؛ افشای `ENCRYPTION_KEY` مسیر دو-مرحله‌ای (decrypt با کلید قدیم → re-encrypt با کلید تازه) نیاز دارد — هرگز فقط کلید را عوض نکنید، داده‌های `enc:v1:...` بی‌پاسخ می‌مانند.

## ۳. اقدام (Action)

### گام ۱ — تولید کلیدهای تازه

```bash
openssl rand -hex 32   # AUTH_SECRET جدید
openssl rand -hex 32   # ENCRYPTION_KEY جدید (فقط پس از گام ۲)
openssl rand -hex 32   # WEBHOOK_SECRET جدید
```

### گام ۲ — چرخش ENCRYPTION_KEY با بازرمزنگاری (اگر افشا شده بود)

داده‌های حساس با الگوی `enc:v1:...` (ماژول `@commerce-os/security`) ذخیره می‌شوند. ترتیب درست:

1. کلید قدیم را موقتاً نگه دارید (مثلاً `ENCRYPTION_KEY_OLD`) و اسکریپت بازرمزنگاری را بنویسید: برای هر فیلد رمزشده، `decrypt` با کلید قدیم و درج `encrypt` با کلید تازه، در تراکنش‌های دسته‌ای (batch) و با لاگ پیشرفت.
2. جدول‌های درگیر را از اسکیما استخراج کنید (هر فیلد `@db.Text` یا `@db.VarChar` که مقدار `enc:v1:` دارد — شماره کارت و شبا و کد ملی و مانند آن). شمارش رکورد درگیر قبل از شروع را ثبت کنید.
3. بازرمزنگاری را روی یک محیط کپی (staging از بکاپ RB-06) تمرین و صحت (دیکود کامل، بدون خطا) را تأیید کنید؛ سپس روی پروداکشن با نرخ کنترل‌شده اجرا کنید.
4. پس از اتمام، کوئری `WHERE field LIKE 'enc:v1:%'` باید همه رکوردها را با قالب کلید تازه نشان دهد و هیچ رکوردی با الگوی قدیم نمانده باشد؛ کلید قدیم را پس از نگهداری محدود برای اثبات ریشه‌کنی، از همه محیط‌ها حذف کنید.
5. اگر افشای ENCRYPTION_KEY شواهدی از سوءاستفاده فعال ندارد ولی زمان طولانی است، بازرمزنگاری می‌تواند در بازه برنامه‌ریزی‌شده انجام شود؛ چرخش AUTH_SECRET/WEBHOOK_SECRET نباید منتظرش بماند.

### گام ۳ — استقرار کلیدهای تازه

```bash
cd /path/to/shop
# .env را با مقادیر تازه ویرایش کنید (بازنویسی با ادیتور، نه echo در ترمینال مشترک)
docker compose -f docker-compose.prod.yml up -d --force-recreate api worker
```

اثر هر کلید پس از چرخش (مطابق سند استقرار، بخش ۸):

| کلید | اثر چرخش | اقدام جبرانی |
|---|---|---|
| `AUTH_SECRET` | اعتبارسنجی توکن‌های صادرشده قبلی شکست می‌خورد؛ همه نشست‌ها عملاً می‌میرند | با گام ۴ پاکسازی کامل کنید؛ کاربران دوباره OTP می‌گیرند |
| `WEBHOOK_SECRET` | گیرنده‌های وب‌هک امضای جدید را باید با کلید تازه تأیید کنند | قبل از recreate، به همه گیرندگان کلید تازه را از کانال امن بدهید |
| `ENCRYPTION_KEY` | داده‌های رمزشده قبلی بدون بازرمزنگاری ناخوانا می‌شوند | گام ۲ |

### گام ۴ — ابطال همه نشست‌ها

```sql
TRUNCATE TABLE user_sessions;
```

یا برای محیط‌هایی که ابطال تدریجی می‌خواهند: `DELETE FROM user_sessions WHERE expires_at > NOW();` — پس از آن همه کاربران باید با `POST /v1/auth/otp/request` و `verify` دوباره وارد شوند. پنجره بین چرخش و truncate را حداقل نگه دارید (توکن‌های قدیمی با AUTH_SECRET تازه از قبل نامعتبرند؛ truncate رکوردهای یتیم را هم پاک می‌کند).

### گام ۵ — حذف Secret از تاریخچه گیت

> مخزن را ابتدا فریز کنید (push/PR موقتاً بسته) و از همه اعضا clone تازه بگیرند؛ تاریخچه بازنویسی‌شده با history قدیمی ناسازگار است.

```bash
# 1) پشتیبان کامل از مخزن (mirror)
git clone --mirror <repo-url> shop-backup.git

# 2) پاکسازی مقدار/فایل از تمام تاریخچه
pipx install git-filter-repo
git filter-repo --path .env --invert-paths   # حذف کل مسیر .env از تاریخچه
# یا فقط جایگزینی مقدار مشخص در تمام blobs:
#   git filter-repo --replace-text <(echo "LEAKED_VALUE==>REMOVED")

# 3) push اجباری تاریخچه بازنویسی‌شده + همگام‌سازی همه cloneها
git push --force --all
git push --force --tags
```

- پس از بازنویسی: هر کسی که clone/فورک/آینه دارد باید `git clone` تازه بگیرد؛ PRهای باز را rebese کنید.
- اگر افشا در سرویس خارجی (GitHub/GitLab) رخ داده، درخواست پاکسازی کش/فورک‌های مدیریتی آن سرویس را هم ثبت کنید و اگر مخزن عمومی است، فرض کنید Secretها تا ابد افشا شده‌اند — چرخش اجباری است، حذف history کافی نیست.

### گام ۶ — تأیید مهار

```bash
curl -f http://127.0.0.1:4000/v1/health      # ok
curl -f http://127.0.0.1:4000/v1/ready       # ready
node scripts/e2e-golden-path.mjs             # سبز (شامل auth/checkout)
docker compose -f docker-compose.prod.yml logs --tail 100 worker   # وب‌هک‌ها با امضای تازه DELIVERED
```

- ورود آزمایشی با OTP: توکن تازه صادر و `GET /v1/auth/me` جواب بدهد.
- یک رویداد وب‌هک آزمایشی بفرستید (`POST /v1/webhooks/test`) و تأیید امضا در سمت گیرنده را بچک کنید.
- بازرمزنگاری ENCRYPTION_KEY: یک رکورد PII نمونه decode شود و مسیر خواندن پنل ادمین سالم باشد.

## ۴. بازگشت (Rollback)

- **Secret چرخیده برنمی‌گردد.** بازگشت به Secret قبلی، رخنه را زنده می‌کند؛ هرگز انجام ندهید.
- اگر بازرمزنگاری نیمه‌تمام ماند: با بکاپ RB-06 همان جداول را به وضعیت قبل بازگردانید و کلید قدیم را موقتاً بازگردانید تا سرویس پاسخ‌گو بماند؛ سپس گام ۲ را با batch کوچک‌تر از نو بچینید.
- اگر `git filter-repo` history را خراب کرد: از `shop-backup.git` بازگردانی کنید و در تلاش دوم فقط `--replace-text` محدود به مقدار افشاشده را اجرا کنید.
- نشست‌های truncate‌شده قابل بازگشت نیستند (عمداً)؛ در پیام به کاربران اعلام ورود مجدد کنید.

## ۵. پیگیری و پیشگیری

- `.env` را در `.gitignore` نگه دارید (وضعیت فعلی مخزن) و همه محیط‌های توسعه را از `.env.example` بچینند؛ کامیت `.env` یک رخداد امنیتی مستقل است.
- اسکن خودکار secrets در CI (gitleaks/trufflehog) با fail روی یافته فعال کنید.
- چرخش دوره‌ای برنامه‌ریزی‌شده (مثلاً فصلی) برای `AUTH_SECRET` و `WEBHOOK_SECRET`؛ `ENCRYPTION_KEY` فقط با همین ران‌بوک و بازه از پیش اعلام‌شده.
- دسترسی لاگ‌ها و `.env` پروداکشن را به حداقل افراد محدود کنید؛ لاگ‌گذاری bodies ممنوع است (قاعده §۷.۱ سند معماری) تا secretها از این مسیر نشت نکنند.
